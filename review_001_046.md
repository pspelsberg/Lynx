# Review: TASK-001 through TASK-046

## Scope and baseline

This is a code/test review of `src/lynx_harness` against `task.md`; no source files were changed.  The mandated suite currently passes (`45` tests, `1` skipped), but most tests exercise only happy paths and do not cover the release-gate/adversarial cases below.

## Prioritized findings

### F-001 — **P0** — Controller is not an execution gate; recursive delegation is broken and child risk can escalate

**Tasks:** TASK-003, TASK-004, TASK-006, TASK-020, TASK-021.

* `loop.py:112-133` invokes `controller.delegate()`/`await_child()` only for the first delegation.  After the child completes it transitions to `checking` (`loop.py:127`), but never transitions back to `executing`; a second model `delegate` therefore raises an illegal transition.  Thus the advertised multi-level RAH chain cannot run.
* The same block validates only parent ID/depth (`loop.py:117`).  It never compares `task.max_risk` with `contract.security.max_risk`.  A model can request `EXTERNAL_MUTATION`/`DANGEROUS` for a child even when the parent contract is read-only; `LocalChildExecutor` then treats the model-supplied child value as the firewall (`rah.py:43-45, 99-105`).
* Normal tool decisions are executed at `loop.py:160-181` without checking controller state or `contract.allowed_tools`; the allowlist is checked only later by `PolicyCheck` (`verifier.py:90-98`).  A disallowed tool can therefore execute before the finish verifier rejects the run.

The controller must be consulted before every action and child limits must be intersected with (not selected by) the parent policy.

### F-002 — **P0** — The “global” ledger does not account all bounded resources, and root cancellation/deadline does not reach a child

**Tasks:** TASK-002, TASK-005, TASK-006, TASK-020, TASK-026.

* `BudgetLedger.DIMENSIONS` omits `max_wall_time_s` (`models.py:383-407`).  `python_seconds` is present but no runner or executor reserves/consumes it (`loop.py:72-99`, `rah.py:93-117`), so a run can exceed those contract dimensions while the ledger reports success.
* `loop.py:123` awaits `child_executor.execute(task)` directly.  The root deadline and `CancellationToken` are not passed or wrapped around this await.  Cancellation during a child and a root deadline expiring while a child runs do not stop that child; only the child-local timeout is used (`rah.py:107-111`).
* `BestOfNExecutor` clones an independent `ComputeBudget` per branch (`bestofn.py:22-32`) and accepts no shared `BudgetLedger`, so parallel branches can multiply root work outside the global ledger.
* When a contract is supplied, a caller-provided `budget` is accepted without checking it against `contract.budget` (`loop.py:60-63`).  The caller can therefore run a contract with larger steps/tokens/tool limits than the immutable contract snapshot.

A root-owned reservation/cancellation scope is needed around every descendant and every resource dimension, and execution must always clamp/validate budgets against the contract.

### F-003 — **P0** — Artifact-only handoff is only a string-prefix check, not a verified manifest/branch boundary

**Tasks:** TASK-022, TASK-023, TASK-025.

`ChildTask.context_firewall()` only checks that strings start with `artifact://` and have no `..` (`rah.py:39-52`).  It does not require the reference to exist, hash it, record origin/size/trust/branch, or reject a reference from another branch.  `LocalChildExecutor` merely calls `ArtifactStore.get` (`rah.py:90-91`), and `ArtifactStore.get` accepts any filename under the store (`memory.py:33-40`) without checking a provenance record.  Consequently a child can receive an arbitrary existing artifact (including one created by another task), and malformed references such as `artifact://dir/name` pass the child check but fail only later in the store.  The required input manifest and replay-safe provenance are absent.

### F-004 — **P0** — Required postconditions and contract policy checks can pass without checking the requirement

**Tasks:** TASK-006, TASK-010, TASK-012, TASK-013, TASK-014.

* `PostconditionCheck` treats `artifact_exists` as satisfied when the candidate contains zero artifact references (`verifier.py:104-114`); it loops over an empty tuple rather than requiring at least one artifact.
* For an unknown postcondition, the mere presence of a key in `context["postcondition_checks"]` suppresses failure; the registered callback is never called (`verifier.py:115-119`).  A custom required check can therefore be marked satisfied without executing it.
* `no_external_mutation` reads `context["external_mutations"]`, but the loop never supplies that field (`loop.py:141`), so this required check cannot observe mutations.
* Contract tool allowlisting is not enforced before execution (see F-001), making finish-time `PolicyCheck` too late for a side-effecting tool.

These checks need explicit callback invocation, non-empty/reference validation, and an execution-time policy gate.

### F-005 — **P0** — Child result verification/merge is incomplete and can reject a verified child status

**Tasks:** TASK-011, TASK-014, TASK-023.

`ChildResult.validate` allows statuses such as `success` and `complete` but not `verified` (`rah.py:70-80`), while the parent’s status gate accepts only `success`, `complete`, and `incomplete` (`loop.py:128-129`)—not the separately allowed `completed` status.  A child runner under a contract can return `state.status == "verified"` on a passed finish (`loop.py:141-148`), so that result is rejected as an invalid child result.  The child result’s `usage`, `claims`, and artifact references are only shallowly bounded (`rah.py:54-80`); there is no usage schema, claim status/provenance validation, or artifact hash/provenance.  In the parent, `child_result.validate` is followed by a status test that unconditionally accepts `incomplete` and then appends a note; there is no `MergeProposal`, child verifier result gate, or root-state merge event.  This does not meet the required explicit child-result and merge gate.

### F-006 — **P0** — Research “verification” is presence checking, and unresolved claims can be promoted to knowledge candidates

**Tasks:** TASK-042, TASK-043, TASK-044, TASK-045, TASK-046.

* `research.py:95-104` ranks only HTTPS, a non-`www` host, and presence of a title; it has no primary-source rule or auditable quality signal, and duplicate detection is URL-only (not content-hash based).
* `research.py:122-129` sets every claim to `passed`/`verified=True` when a source has a URL and the excerpt/claim are non-empty.  No claim-level check establishes that the excerpt supports the claim; this is explicitly weaker than the required evidence contract.
* Contradictions are set to `pending` (`research.py:130-142`), but `research.py:153` returns `complete` whenever there is any synthesis (the `else` branch also returns `complete` even when all claims are unverified).  The synthesis path does not require citations or include unresolved-conflict markers (`research.py:148-151`).
* `research.py:154-155` writes a candidate whenever synthesis exists, including evidence that has not passed a real claim verifier.  `OkfStore` has no staging state, and `promote_candidate` accepts an arbitrary string (`memory.py:74-81`) rather than a verifier result/check IDs and writes no verification event/provenance.  This leaves the TASK-046 promotion gate unenforced by the store API.

### F-007 — **P0** — Child execution is not recorded as a child trajectory, so lineage/replay is incomplete

**Tasks:** TASK-006, TASK-020, TASK-023, TASK-025.

`LocalChildExecutor` creates/runs the child runner without injecting a recorder, trajectory, parent task ID, or parent event (`rah.py:99-117`).  The parent records only a summary `child_result` (`loop.py:124-126`).  Thus child decisions, tool observations, budgets, and verification events are absent from the run’s Flight Recorder; the parent/child run cannot be reconstructed or replayed from the recorded events as required.

### F-008 — **P1** — RepairLoop exists only as an unused callback utility and has no repair budget/policy firewall

**Tasks:** TASK-013, TASK-024.

`RepairLoop.run` (`verifier.py:145-157`) retries a caller-supplied callback but does not consume any budget, enforce a deadline, or constrain the callback from invoking tools.  `AgentRunner` never calls it: a failed/incomplete finish is immediately returned (`loop.py:134-149`).  Schema/postcondition failures therefore do not produce the specified bounded repair path, and the repair callback itself is not a safe policy boundary.

### F-009 — **P1** — RLM context compaction is wired in, but bounded RLM Map/Reduce and evaluation integration are not

**Tasks:** TASK-030, TASK-031, TASK-032, TASK-033, TASK-034, TASK-035.

`AgentRunner` calls `RlmContextEngine.prepare` only when serialized context exceeds the threshold (`loop.py:87-92`); it never invokes `RlmExecutor` or `map_reduce`.  The exported `map_reduce` gathers arbitrary mapper callbacks with no ledger reservation, timeout, cancellation, or per-call budget (`context.py:90-94`).  The evaluator’s `rlm`/`rah` variants are labels only (`eval.py:12`), while `build_runner` changes neither context strategy nor RAH wiring for those variants (`cli.py:21-39`).  Even the `+verification` variant does not pass a `Verifier` into `AgentRunner`; the only variant-specific change is enabling the progress monitor (`cli.py:38-39`).  The claimed ablation therefore cannot measure normal-context versus RLM, RAH, or verifier behavior.

### F-010 — **P1** — Flight replay cannot reproduce a delegate decision

**Tasks:** TASK-025.

`ReplayBackend.decide` handles `tool` and `finish`, but every other recorded decision—including `delegate`—is converted to `reflect` (`flight.py:148-153`).  A recorded parent-child run would take a different action during replay, and there is no child replay executor.  This violates deterministic replay and fork continuation for RAH runs.

### F-011 — **P1** — Persisted trajectory records use a different event schema than the trajectory dataset exporter

**Tasks:** TASK-006 and the trajectory/replay slice underpinning TASK-025.

`AgentRunner._record` writes JSONL records with `kind` (`loop.py:39-50`), while `TrajectoryDataset.add_run` searches for `type` (`training.py:21-27, 29-38`).  Actual runner trajectories therefore contain no `decision`, `run_started`, `run_finished`, or `verification` events as far as the exporter is concerned, and a recorded successful run exports zero examples.  The recorder uses `type`, so the two append-only event formats should be unified or explicitly adapted before audit/replay consumers rely on them.

### F-012 — **P1** — Research freshness check crashes for common date strings

**Tasks:** TASK-040, TASK-042, TASK-044.

`check_freshness` parses a date without an offset as a naive `datetime` and subtracts it from an aware UTC `now` (`research.py:60-69`), raising `TypeError` instead of marking stale.  It also silently ignores malformed dates.  A regression test should cover both naive and offset timestamps and require a visible stale/pending outcome.

### F-013 — **P1** — “Strict” budget/contract validation accepts booleans/floats for integer limits and accepts unusable artifact references

**Tasks:** TASK-001, TASK-002.

`ComputeBudget.__post_init__` and `BudgetLedger.__init__` use `isinstance(value, int)` / `(int, float)` without rejecting `bool` (`models.py:309-325`, `models.py:391-397`), and the ledger permits fractional values for token/step/call dimensions.  This undermines strict transport validation and can make comparisons/accounting nonsensical.  `_artifact_ref` permits slash-containing references (`models.py:41-44`) that `ArtifactStore.get` rejects (`memory.py:34-36`), so a contract can validate and then be unexecutable.  Integer dimensions need exact type/range checks and artifact references need one canonical parser.

## Existing test evidence and gaps

`uv run python -m unittest discover -s tests -v` passes (45 tests, one live-llama test skipped).  The suite does not currently test: a second/deeper child, parent-vs-child risk escalation, pre-execution contract allowlists, wall-time/python ledger exhaustion, cancellation while a child runs, artifact provenance/foreign branch references, required empty `artifact_exists`, callback invocation for custom postconditions, verified child status, repair integration, RLM map/reduce budgeting, delegate replay, claim truth/contradiction promotion, or naive-date freshness.
