# Review: TASK-050 through TASK-103

## Scope and test baseline

Reviewed `src/lynx_harness`, `tests`, `evals/smoke.json`, `config/model-manifest.json`, scripts, and the runbook against `task.md`. The local suite passes (`45` tests, with the live llama test skipped unless `LYNX_INTEGRATION=1`), but most slice tests exercise only happy paths and do not prove the acceptance criteria below. Findings are ordered by release/safety impact.

## Findings

### P0 — RAH delegation cannot execute through the implemented child executor (TASK-020–026)

`parse_decision()` constructs `models.AgentTask` for a `delegate` decision (`src/lynx_harness/inference.py:78-90`), and `AgentRunner` passes that object directly to `child_executor.execute()` (`src/lynx_harness/loop.py:112-133`). The supplied `LocalChildExecutor` requires a `rah.ChildTask` and immediately calls `task.context_firewall()` (`src/lynx_harness/rah.py:88-91`). `models.AgentTask` has no such method, so a real delegate is rejected/recorded as a delegation failure rather than running a child. There is no two-level integration test; `tests/test_rah.py:19-43` only invokes the executor directly with `ChildTask`, and the parent loop is never exercised with `DELEGATE`.

**Impact:** the release gate's bounded two-level RAH run, child result verification, and replay lineage are not reachable. Add an explicit, validated conversion/one canonical task model and an end-to-end parent→child→result test (including depth 2 and depth 3 rejection).

### P0 — Task-contract tool allowlists and security limits are not enforced before side effects (TASK-051, 055, 090, 102)

`AgentRunner` exposes either all registry tools or keyword-retrieved tools (`src/lynx_harness/loop.py:80-82`) and executes the model-selected name through the gateway (`src/lynx_harness/loop.py:160-181`). `ToolGateway` checks only its standalone `ToolPolicy` (`src/lynx_harness/tools.py:152-165`); it has no contract/allowed-tools argument. Although `Verifier.PolicyCheck` can report a tool outside `contract.allowed_tools` after the fact (`src/lynx_harness/verifier.py:88-98`), the external/local action has already run. `AgentRunner.run()` also never intersects `contract.security.max_risk` or its allowlist with the gateway policy (`src/lynx_harness/loop.py:60-67`).

**Impact:** a contract promising no external tools can still perform them if the runner gateway is permissive; verification is not a prevention gate. Bind an immutable per-run policy to the contract and enforce allowlist/risk before every call, including child and adapter paths. Add tests that assert the handler is never invoked.

### P0 — Verified trajectory export is caller-forgeable and accepts incomplete audit records (TASK-073, 091)

`TrajectoryDataset.add_run()` trusts the caller's `verified=True` and treats missing `run_finished` and `verification` events as acceptable because those checks are conditional (`src/lynx_harness/training.py:21-28`). Thus a bare `run_started` plus a finish decision exports an example when the caller sets `verified=True`; the existing test demonstrates exactly this (`tests/test_training.py:6-10`). It also writes the unredacted goal into `base` (`src/lynx_harness/training.py:28`), while only observations/actions are redacted. Dataset output has no model/task-family split, verifier check IDs, or robust run/event identity beyond the optional fields (`src/lynx_harness/training.py:31-43`).

**Impact:** unverified or secret-bearing data can enter training. Derive acceptance solely from a complete, cryptographically/audit-linked passed verifier result; require explicit successful finish; redact every field including goal; reject malformed event schemas; and implement split metadata. Add tests for missing/forged verification and secrets in goals, arguments, error text, and artifacts.

### P0 — Skill promotion has a direct evidence bypass (TASK-056–057)

`SkillRegistry.promote()` promotes any matching-version manifest when the caller supplies `{"passed": true}` (`src/lynx_harness/skills.py:66-73`), without requiring a `SkillEvaluation`, replay case IDs, verifier/safety evidence, or even checking that the current status is `candidate`. The standalone test promotes this arbitrary flag (`tests/test_additional_slices.py:23-27`). `SkillExecutor` likewise executes registered manifests without validating `inputs`/`outputs` schemas or candidate/stable lifecycle (`src/lynx_harness/skills.py:28-42`).

**Impact:** an untested/riskier skill can become stable, contrary to the no-automatic-promotion/release safety gate. Make promotion accept only a validated evaluation object persisted from replay, require candidate status and non-regression in verifier/safety/latency metrics, and validate manifest schemas and lifecycle at execution.

### P1 — RAH repair, child verification, and parent merge are not integrated (TASK-023–025)

`RepairLoop` is an isolated callback utility (`src/lynx_harness/verifier.py:145-157`); `AgentRunner` has no repair path after child/result verification. `LocalChildExecutor` runs a child without a contract verifier (`src/lynx_harness/rah.py:105-117`), then returns a `ChildResult` whose `verification`, `claims`, and `usage` are not populated. In the parent, any `success`, `complete`, or even `incomplete` child status is accepted (`src/lynx_harness/loop.py:123-130`), with no merge gate. `BranchManager.merge()` is a separate API and only verifies `{"answer": ...}` (`src/lynx_harness/branch.py:46-56`).

**Impact:** verifier failure does not trigger bounded repair, and the claimed ChildResult/merge acceptance criteria are not met. Wire child checks, max repair budget/attempt events, artifact existence, and an explicit verified merge into the controller; reject incomplete child output.

### P1 — Progressive tool disclosure is only keyword sorting and has no quality fallback (TASK-050)

`ToolRegistry.retrieve()` tokenizes text and ranks by substring matches (`src/lynx_harness/tools.py:85-94`), always returning up to `limit` tools even when every score is zero. `AgentRunner` immediately adds every selected tool's full `input_schema` (`src/lynx_harness/loop.py:80-82`) and hard-codes `limit=6`; there is no model-dependent limit, retrieval-quality threshold, fallback policy, or second request to disclose a schema on demand. `ToolSpec.summary()` supports a summary but is not used for a true progressive two-stage disclosure (`src/lynx_harness/models.py:258-260`).

**Impact:** prompt size/selection accuracy cannot be compared with “all tools,” and irrelevant schemas are exposed. Implement score/quality thresholds, family routing, configurable top-k, summary-first prompts, and audited schema disclosure/fallback; add precision/recall and prompt-size tests.

### P1 — Adapter policy/audit contracts are inconsistent (TASK-051–055)

* MCP ignores its configured risk: discovery hard-codes every discovered tool to `EXTERNAL_MUTATION` (`src/lynx_harness/mcp.py:62-74`), and there is no persisted handshake/capability audit record. Dynamic registration remains possible unless callers remember to freeze the registry (`src/lynx_harness/tools.py:67-74`).
* MCP's timeout cleanup exists, but the client does not normalize errors/retries into common classes, and its response is only line-size bounded (`src/lynx_harness/mcp.py:39-54`); there is no server-level output/cleanup audit integration.
* LSP returns raw results and has a 2 MB transport bound but no common output/risk/provenance/timeout adapter (`src/lynx_harness/lsp.py:40-45`).
* Browser and kernel adapters are only normalized if manually registered through the gateway; no shared adapter interface enforces the same metadata/rules.

The common `Observation` fields exist, but this is not evidence that every enabled adapter uses identical retry, limit, confirmation, and provenance behavior. Add an adapter protocol and contract tests for each adapter, freeze/revalidate registries, and audit handshake/configuration snapshots.

### P1 — Playwright is not a browser session and an empty allowlist self-allows any host (TASK-053)

Every operation launches a new CLI process (`src/lynx_harness/playwright.py:17-27`), so navigation state/session lifecycle and reliable cleanup are absent. For `open`, it calls `_safe_url(url, self.allow_hosts or {host})` (`src/lynx_harness/playwright.py:20-22`), which turns an empty configured allowlist into “allow the requested host”; this is not a domain allowlist. `open`, `snapshot`, `click`, and `fill` all share `EXTERNAL_MUTATION` risk (`src/lynx_harness/playwright.py:30-33`), and browser `timeout_s` is not validated. No browser fixture or confirmation regression exists; the sensor test only checks that a missing binary errors (`tests/test_sensors.py:23-25`).

**Impact:** opt-in browser actions can navigate any public domain and do not satisfy lifecycle/download-upload/confirmation acceptance. Require a nonempty configured allowlist (never derive it from input), persistent owned session with `finally` cleanup, operation-specific risk, bounded downloads/uploads, and fixture tests.

### P1 — Python “sandbox” lacks the required process/resource boundary (TASK-054, 092)

The implementation explicitly admits it is not a security sandbox (`src/lynx_harness/kernel.py:40-46`). It sets only a hard-coded 1 GiB address-space and CPU limit (`src/lynx_harness/kernel.py:47-53`), with no configurable RAM/FD/process/output/disk limits. The audit hook blocks a few obvious calls but does not establish a robust syscall/filesystem boundary; generated code can import escape primitives (for example, native/ctypes mechanisms) or use unhandled process APIs. There is no per-task/branch identity or artifact-only capability; the worker is persistent for a `PythonKernel` instance (`src/lynx_harness/kernel.py:47-63`). Tests cover only persistence, a socket attempt, and timeout (`tests/test_kernel.py:8-23`).

**Impact:** TASK-054's path-escape, memory-limit, network, timeout, and self-escalation acceptance is unproven. Use an actual OS/container sandbox or explicit deny-by-default capability design, set all resource limits, isolate each task/branch, and test bypasses and cleanup.

### P1 — Capability profiles/model auto-selection are dead configuration; manifest/download enforcement is incomplete (TASK-060–063, 066)

`CapabilityProfile` and `select_capability()` exist (`src/lynx_harness/model_profiles.py:43-64`), but `build_runner()` constructs `LlamaCppBackend` with no profile (`src/lynx_harness/cli.py:21-39`). Consequently model changes do not select mode-specific tool/step/sampling/thinking profiles, and TASK-066's quality-first fallback/audit cannot occur. The only live llama integration test checks `/health` (`tests/test_integration_llama.py:10-14`), not chat-template, JSON, thinking, or 4B/9B/27B behavior.

The manifest has entries, but model download is hard-coded to the 4B URL/file/hash (`scripts/download-model.sh:4-18`) rather than consuming and validating manifest entries. `ModelManifestEntry.validate_download()` runs only when `verify_file()` is called (`src/lynx_harness/model_profiles.py:21-30`), and `build_runner()` merely hashes an arbitrary configured file without comparing it to a manifest entry (`src/lynx_harness/cli.py:29-36`). There is therefore no start-time refusal for a wrong model/revision/hash.

### P1 — RX-9060 XT profiler matrix cannot run its own default and does not measure the required workload (TASK-064)

`LynxBenchmarkMatrix.profiles()` generates 216 combinations (3 models × 2 backends × 3 contexts × 3 slots × 2 thinking × 2 flash) (`src/lynx_harness/profiler.py:258-270`), while `run_profile_matrix()` rejects more than 64 profiles (`src/lynx_harness/profiler.py:187-205`). The matrix omits 9B Q6/Q8, fast/think/research workload modes, and actual task-success measurements; `BenchmarkResult` has only generic score/throughput/latency/memory and no p50/p95, VRAM, verifier/task success, or failure/driver metadata (`src/lynx_harness/profiler.py:91-119`). There is no generated profile/run artifact or profiler test beyond a synthetic two-profile score (`tests/test_profiler.py:5-10`).

**Impact:** no acceptance evidence for ROCm/Vulkan, 4k/8k/16k, 1/2/3 slots, or mode quality. Split the matrix into bounded batches and record reproducible server/model/driver/commit metrics and task outcomes.

### P1 — Evaluation claims metrics and ablations that are not implemented (TASK-070–073)

`evals/smoke.json` contains only no-tool, calculator, and a policy-injection prompt (`evals/smoke.json:1-20`); it has no invalid-argument retry, multi-tool, RLM, RAH merge/reject, research claims/contradictions, MCP/browser/CLI/kernel fixtures, or adversarial payload cases. More importantly, `AblationEvaluator` invokes the same factory/run for all variants (`src/lynx_harness/eval.py:41-56`); `build_runner()` only changes tool-router/progress behavior (`src/lynx_harness/cli.py:21-39`), so `rlm`, `rah`, and `rah+verifier` are not distinct ablations.

Several reported fields are placeholders or wrong: `retry_success_rate`, citation precision, research coverage, RAH child success, and merge rejection are never populated (`src/lynx_harness/eval.py:56-66`), and `verification_passed` treats ordinary `success` as verified. VRAM is not recorded at all. Thus aggregate numbers can look complete while measuring none of the required metrics. Add fixture-backed variant wiring, per-case expected tools/postconditions/status, verifier/child/citation instrumentation, and “missing data is not success” handling.

### P1 — RLM/Research/trajectory paths are not globally bounded/auditable in the production loop (TASK-030–045, 094)

`RlmExecutor` can reserve recursive calls in an optional ledger, but map/reduce launches `asyncio.gather()` directly and has no timeout/cancellation/ledger accounting (`src/lynx_harness/context.py:90-94`). `AgentRunner`'s context compaction is thresholded, but RLM context calls are not integrated as a controller strategy or ablation; no global RLM budget is charged in `AgentRunner` (`src/lynx_harness/loop.py:87-97`).

Research marks claims as passed based on a nonempty URL/excerpt/first sentence (`src/lynx_harness/research.py:122-129`) rather than an independent semantic/verifier check; targeted-search source records omit retrieval timestamp/content hash/ranking metadata (`src/lynx_harness/research.py:143-147`). The workflow unconditionally creates a knowledge candidate (`src/lynx_harness/research.py:148-155`) without preserving full claim/source provenance in the candidate. Add bounded/cancellable map-reduce accounting and claim-level verification fixtures; ensure unsupported/contradictory claims remain pending and promotion cannot happen from this workflow alone.

### P1 — Global resource governance and cancellation are local, not global (TASK-026, 092–093)

`ToolGateway` creates a semaphore per instance (`src/lynx_harness/tools.py:146-150`), while `build_runner()` creates a fresh gateway for every run (`src/lynx_harness/cli.py:21-26`); there is no process-wide tool/child/slot/FD/VRAM governor. Child scheduling is only a local semaphore plus `gather()` (`src/lynx_harness/rah.py:127-137`), and a child exception/cancellation is not isolated with a structured result. `AgentBus.cancel()` only sets an event (`src/lynx_harness/agent_bus.py:32-39`); a running handler is not interrupted, and `close()` cancels the worker without cancelling/finishing the handler (`src/lynx_harness/agent_bus.py:40-41`).

The API semaphore limits only four requests and has a racy `locked()` pre-check (`src/lynx_harness/api.py:44-54`); it does not provide global child/process/VRAM limits, request cancellation, or durable timeout cleanup. Add one shared governor, structured cancellation propagation, per-resource limits, and leak tests.

### P1 — A2A surface is synchronous-only, under-limited, and does not treat remote results as untrusted (TASK-081–083)

`A2AClient.submit()` returns arbitrary decoded JSON without validating `AgentResult`, status, artifact refs, or marking it untrusted (`src/lynx_harness/a2a.py:61-68`). A timeout around `asyncio.to_thread()` does not stop the blocked network thread. The FastAPI surface accepts an unbounded `dict` body before task bounds are checked, runs the executor synchronously, and exposes only `POST /tasks`—no status polling, artifact retrieval, cancellation, or streaming lifecycle (`src/lynx_harness/a2a.py:79-91`). The “interoperability” implementation is an in-process `A2AReplayStub` (`src/lynx_harness/a2a.py:107-120`), and tests only check model construction, route existence, and HTTPS validation (`tests/test_a2a.py:6-16`), not a real compatible implementation.

**Impact:** TASK-082/083's request/output limits, lifecycle, and interoperability evidence are absent. Add bounded request models, authenticated/authorized task state endpoints, remote result validation/trust labels, cancellable transport, and a nonsecret real/stub protocol fixture that covers discovery/submit/status/artifact/failure.

### P1 — Secret redaction is incomplete for artifacts and common URL/query forms (TASK-091)

String artifacts are passed through `redact_text`, but byte artifacts bypass redaction (`src/lynx_harness/memory.py:18-31`). `redact_text` only recognizes credentials in URL authority and a small key/value pattern (`src/lynx_harness/security.py:5-11`), so query credentials and many header/env/error formats can persist. It also truncates every redacted string to 10,000 characters, silently changing artifact content. `TrajectoryDataset` additionally stores the raw goal as noted above. Tests cover only one nested key and a bearer string (`tests/test_foundations.py:27-31`).

Add structured secret sources (headers, env values, cookies, URL query), redact before every artifact/A2A/flight sink including bytes where appropriate, preserve bounded content separately from redaction, and test nested/error/query cases.

### P1 — Flight/replay lineage and audit schema are not complete (TASK-025, 094)

`FlightRecorder` has schema/version fields and IDs, but its manifest contains only IDs/timestamp (`src/lynx_harness/flight.py:47-55`); model/backend/policy/budget snapshots are only opportunistically placed in a `run_started` event by `AgentRunner` (`src/lynx_harness/loop.py:69-74`), and record readers do not validate schema versions or provide migrations (`src/lynx_harness/flight.py:85-88`). `build_runner()` does not pass task/parent IDs to the recorder (`src/lynx_harness/cli.py:36-39`). The CLI `replay` command only counts/types events (`src/lynx_harness/cli.py:103-107`), rather than executing a deterministic ReplayBackend/Gateway replay; delegate decisions are also not reconstructed by `ReplayBackend` (`src/lynx_harness/flight.py:135-153`).

**Impact:** child/root reconstruction and “replayable complete parent-child run” are not demonstrated. Persist complete immutable snapshots and lineage in the manifest/event schema, validate versions, support delegate events, and make replay CLI actually run/verify without external calls.

### P2 — API/operation runbook and architecture fitness evidence are incomplete (TASK-093, 100–102)

`docs/architecture.md` contains one compact diagram but does not explicitly show the external A2A surface, OKF/trajectory layers, or security boundaries required by TASK-100. `docs/runbook.md` is only seven bullets (`docs/runbook.md:1-8`): it has no reproducible model hash, ROCm/Vulkan build, profiler/live-integration commands, resume/fork procedure, or incident steps required by TASK-101. There are no systemd templates.

The sole architecture test checks only that runtime does not import `tests`/vendor modules (`tests/test_architecture.py:8-21`). It does not test dependency-free core, gateway-only external actions, loop URL/subprocess boundaries, default remote binding, or child-policy non-escalation required by TASK-102. TASK-103 has no measurement/decision artifact (which is acceptable as an optional implementation deferral, but should be recorded explicitly).

### P2 — API health leaks configuration and durable-operation controls are missing (TASK-093)

The unauthenticated health response includes `configured.server_url` (`src/lynx_harness/api.py:29-34`), which may contain sensitive URL material, and `/runs` returns up to 100,000 answer characters plus all observations (`src/lynx_harness/api.py:44-57`) without an aggregate response cap. Authentication is required for runs, but there is no TLS/rate-limit/retention/rotation implementation or systemd deployment artifact—only documentation advice.

Return only nonsecret readiness metadata, enforce aggregate request/output limits and cancellation/timeouts, and provide deployment/retention controls before claiming TASK-093 complete.

## Explicitly optional/deferred tasks

TASK-015, TASK-065, TASK-075, TASK-084, and TASK-103 are marked optional/future in `task.md`; absence alone is not a release defect. TASK-065/075 nevertheless have no benchmark/evidence hooks, and TASK-103 has no bottleneck measurement to justify a future Rust boundary.

## Recommended first fixes

1. Fix the task-model mismatch and enforce immutable contract allowlist/risk before any tool call.
2. Make verifier-backed child/merge/repair and trajectory export non-forgeable; add end-to-end RAH tests.
3. Remove promotion/evaluation bypasses and replace placeholder metrics with fixture-backed measurements.
4. Harden kernel/browser/MCP/A2A lifecycle and global resource governance.
5. Integrate model profiles and produce bounded, reproducible ROCm/Vulkan/model/evaluation artifacts.
